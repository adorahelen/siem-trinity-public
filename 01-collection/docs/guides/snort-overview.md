# Snort IDS/IPS 개요 및 적용 판단

> 작성일: 2026-03-10

---

## Snort란

네트워크를 **지나가는 패킷을 실시간으로 검사**하는 NIDS(Network Intrusion Detection System) / NIPS(Network Intrusion Prevention System).

로그 기반 도구와의 근본 차이:

```
로그 기반:  공격 패킷 → 서버 수신 → 처리 → 로그 기록 → Fail2Ban 반응
Snort IPS:  공격 패킷 → Snort 차단 → 서버에 도달 안 함
```

동작하려면 트래픽이 **지나가는 경로에 삽입**되어야 함:

```
인터넷 → [라우터] → [Snort 장비] → 내부 네트워크
                         ↑
                  모든 패킷을 여기서 검사
```

---

## 실제 배포 환경

| 환경 | 구체적 사용처 |
|------|------------|
| 기업 경계 보안 | 인터넷-DMZ 구간, DMZ-내부망 구간에 인라인 배치. 전사 트래픽을 한 곳에서 검사 |
| ISP/통신사 | 가입자 트래픽에서 악성코드 유포, DDoS 탐지 |
| 데이터센터 | 서버 팜 앞단에서 SQL Injection, 웹셸 업로드 탐지 |
| 산업제어망(ICS/SCADA) | Modbus, DNP3 등 프로토콜 이상 패턴 탐지 |
| 보안관제(SOC) | SIEM에 Snort 이벤트를 인풋으로 사용 |

---

## Snort만 할 수 있는 것

로그 기반 도구로는 볼 수 없는 영역:

- **연결 자체가 성공하지 못한 패킷** — 포트스캔, SYN flood는 애플리케이션 로그에 안 남음
- **패킷 페이로드** — HTTP body, DNS 쿼리 내용, 평문 명령어 등
- **세션 중간의 이상 패턴** — 정상 연결 후 셸코드가 삽입되는 경우
- **비표준 포트 우회** — 80번 포트로 SSH를 흉내낸 C2 통신

---

## 이 프로젝트에 적용하지 않는 이유

Snort가 효과적인 조건과 현재 환경 비교:

| 조건 | 현재 상황 |
|------|---------|
| 네트워크 중간에 위치 가능 (스위치 미러링, 인라인 브리지) | 홈서버 단일 노드, 토폴로지 변경 불가 |
| 다수의 내부 호스트를 한 곳에서 감시 | 보호 대상이 서버 1대뿐 |
| 평문 트래픽 검사 가능 | 외부 접근이 Tailscale(WireGuard 암호화) → 패킷 내용 열람 불가 |

또한 현재 스택으로 이미 커버되는 영역:

- 포트/로그인 레이어 → UFW + Fail2Ban
- HTTP 페이로드 탐지 → ModSecurity (향후 도입 예정, 5순위)
- 호스트 내부 침입 탐지 → Wazuh (향후 도입 예정, 6순위)

---

## 대안 비교

| 도구 | 레이어 | 현재 스택 통합 |
|------|--------|--------------|
| Snort | 네트워크 패킷 | 별도 인프라 필요, 현재 환경 부적합 |
| ModSecurity | HTTP 페이로드 | Nginx 모듈로 자연스럽게 통합 가능 |
| Wazuh | 호스트 내부 | 에이전트 설치만으로 통합, 로그를 Loki로 연동 가능 |
| Suricata | 네트워크 패킷 | Snort 대안, 더 현대적이고 JSON 로그 출력으로 Promtail 연동 용이 |

> Snort를 학습 목적으로 다룬다면 이 프로젝트와 별개로 독립된 실습 VM에서 진행 권장.
