# 아웃바운드 제어 및 NAT 불필요성 (2026-03-14)

---

## 1. NAT이 현재 홈서버에 불필요한 이유

### NAT이란?

NAT(Network Address Translation): 사설 IP ↔ 공인 IP를 변환하는 기술.
주로 **하나의 공인 IP로 여러 내부 기기가 인터넷을 쓰기 위해** 공유기가 사용.

### 현재 구조상 필요 없는 이유

| 이유 | 설명 |
|------|------|
| **ISP가 이미 처리** | 공유기가 ISP NAT을 자동 수행. 서버가 직접 NAT 설정할 필요 없음 |
| **서버는 1대** | NAT의 본래 목적(여러 기기 → 공인 IP 1개 공유)이 서버 1대에선 의미 없음 |
| **Tailscale이 NAT 우회 해결** | 외부에서 서버 접속 시 NAT traversal을 Tailscale WireGuard가 처리 |
| **포트 포워딩으로 충분** | 외부 공개가 필요한 포트는 공유기 포트 포워딩으로 해결 |
| **Docker가 내부 NAT 처리** | 컨테이너 ↔ 호스트 간 IP 변환은 Docker가 iptables masquerade로 자동 처리 |

### 만약 NAT 설정이 필요해지는 시점

- 서버 한 대가 내부의 여러 다른 서버를 대신해 외부와 통신해야 할 때
- 기업 환경에서 DMZ 구성 시
- 현재 홈서버 단일 노드 구성에서는 해당 없음

## 2. 악성코드의 아웃바운드 의존성

### 공격자의 사고 흐름

```
[1단계] 침투 (인바운드)
        SSH 브루트포스, 웹 취약점, 악성 첨부파일 등
             ↓
[2단계] 서버 내부에서 실행
        페이로드 드롭, 권한 상승, 지속성 확보
             ↓
[3단계] "유용한 작업" 수행 → 전부 아웃바운드 필요
        ├─ 원격 제어 확보  → 리버스쉘 / RAT → C2 서버 아웃바운드
        ├─ 파일/DB 유출   → 공격자 서버로 전송 (아웃바운드)
        └─ 크립토마이닝   → 채굴풀 연결 (아웃바운드)
```

> 공격자가 서버에 침투했더라도 **아웃바운드가 제어되면 실질적 피해를 주기 어렵다.**

### 아웃바운드 불필요 악성코드 (예외)

| 유형 | 아웃바운드 필요 | 동작 |
|------|----------------|------|
| 랜섬웨어 | ❌ (로컬만) | 파일 암호화 → 로컬에서 완결 |
| 와이퍼 (Wiper) | ❌ | 디스크 데이터 파괴 |
| 로직 폭탄 | ❌ | 조건 충족 시 파괴 실행 |
| **RAT / 리버스쉘** | ✅ 필수 | C2 서버 연결 없으면 제어 불가 |
| **데이터 유출** | ✅ 필수 | 전송 경로 없으면 유출 불가 |
| **크립토마이너** | ✅ 필수 | 채굴풀 연결 없으면 수익 불가 |

공격자가 가장 원하는 목적(원격 제어, 정보 유출)은 **전부 아웃바운드에 의존**.

## 3. 현재 프로젝트의 아웃바운드 대응 현황

```
UFW 기본 정책:     아웃바운드 전체 허용  ← 현재 약점
KR-ONLY (ipset):   인바운드만 제어, 아웃바운드 무관
Suricata:          알려진 C2 IP/도메인 시그니처 탐지 (탐지만)
Zeek conn.log:     아웃바운드 기록 (탐지만, 차단 안 함)
```

악성코드가 실행되면 **현재 구조에서는 아웃바운드가 사실상 자유롭다.**

---

## 4. 개선 방안: UFW 아웃바운드 화이트리스트

### 적용 명령

```bash
# 1. 기본 아웃바운드 거부로 전환
sudo ufw default deny outgoing

# 2. 꼭 필요한 것만 명시적 허용
sudo ufw allow out 80/tcp    # HTTP (패키지 업데이트, apt)
sudo ufw allow out 443/tcp   # HTTPS
sudo ufw allow out 53/udp    # DNS
sudo ufw allow out 123/udp   # NTP (시간 동기화)
sudo ufw allow out 41641/udp # Tailscale WireGuard

# 3. 적용 확인
sudo ufw status verbose
```

### 효과

| 시나리오 | 현재 | 적용 후 |
|---------|------|---------|
| 리버스쉘 → 임의 포트 아웃바운드 | 허용 | ❌ 차단 |
| C2 비표준 포트 통신 | 허용 | ❌ 차단 |
| 크립토마이너 채굴풀 연결 | 허용 | ❌ 차단 (비표준 포트) |
| HTTPS 위장 C2 (443) | 허용 | ⚠️ 통과 (Suricata 탐지 필요) |
| DNS 터널링 C2 | 허용 | ⚠️ 통과 (Zeek 탐지 필요) |

### 주의사항

- 적용 전 현재 서버에서 아웃바운드로 나가는 서비스 전부 확인 필요
- Docker 컨테이너 아웃바운드는 별도 iptables 규칙으로 처리됨
- Wazuh agent → manager 통신 포트 (1514/tcp, 1515/tcp)도 허용 필요

```bash
# Wazuh 통신 (로컬 매니저 사용 시 루프백)
sudo ufw allow out to 127.0.0.1

# 외부 Wazuh 매니저 사용 시
sudo ufw allow out 1514/tcp
sudo ufw allow out 1515/tcp
```

## 5. 계층별 아웃바운드 방어 구조

```
계층            방어 도구              역할
─────────────────────────────────────────────
L3/L4 차단     UFW (deny outgoing)    비허용 포트 아웃바운드 원천 차단
L7 탐지        Suricata ET 룰셋       HTTPS/DNS 위장 C2 시그니처 탐지
행위 분석      Zeek conn.log          비정상 연결 패턴 기록 (빈도, bytes)
호스트 감시    Wazuh 프로세스 모니터  비정상 프로세스가 네트워크 연결 시 탐지
```

인바운드를 막는 것만큼 **아웃바운드 화이트리스트**가 악성코드 피해 최소화의 핵심.
