# Zeek 도입 시 가시성 확장 분석

> 작성일: 2026-03-13
> 대상: `security-log-monitor`
> 전제: 현재 스택은 `UFW + fail2ban + nginx + ModSecurity + Wazuh + Promtail + Loki + Grafana` 중심이며, Zeek는 아직 미도입 상태다.

---

## 1. 핵심 요약

현재 스택은 `로그 기반 보안 모니터링`으로는 충분히 강하다. 다만 네트워크 레이어에서 "누가, 언제, 어떻게 움직였는지"를 전수에 가깝게 남기는 계층은 비어 있다.

Zeek를 도입하면:
- Suricata가 알려주는 "악성 시그니처 탐지"를 넘어
- 세션, DNS, TLS, HTTP 메타데이터를 장기적으로 축적해
- 공격 전 정찰, 우회, 비정상 통신 패턴까지 역추적할 수 있다.

결론:
- `Suricata`는 "뭐가 나쁜지"를 찾는 도구
- `Zeek`는 "그 전에 무슨 일이 있었는지"를 재구성하는 도구

---

## 2. 현재 한계 (Zeek 없이)

현재도 많은 이벤트는 보인다. 하지만 다음 질문에는 답이 약하다.

| 질문 | 현재 스택만으로 답변 가능 여부 | 한계 |
|---|---|---|
| 누가 공격했는가 | 부분 가능 | UFW/fail2ban/nginx/WAF 로그 기준 |
| 공격 전에 어떤 포트를 정찰했는가 | 어려움 | 세션 전수 기록 부재 |
| 룰에 걸리지 않은 스캔/정찰이 있었는가 | 약함 | Suricata/Zeek 미도입 시 네트워크 사각지대 |
| 서버가 외부에 어떤 DNS 질의를 했는가 | 약함 | DNS 전수 로그 부재 |
| TLS 세션에서 어떤 SNI/JA3 패턴이 있었는가 | 불가 | TLS 메타데이터 계층 부재 |
| 공격과 직전 네트워크 행위를 같은 타임라인으로 묶을 수 있는가 | 제한적 | 애플리케이션 로그 중심 |

---

## 3. Zeek 도입 시 얻는 것

### 3.1 네트워크 메타데이터 전수 기록

Zeek는 룰에 걸린 이벤트만 남기지 않는다. 연결 자체를 기록한다.

핵심 로그:
- `conn.log`: TCP/UDP 세션
- `dns.log`: DNS 질의/응답
- `ssl.log`: TLS 핸드셰이크 메타데이터
- `http.log`: 평문 HTTP 요청
- `notice.log`: 내장 이상 탐지 결과
- `weird.log`: 프로토콜 이상 징후

이 덕분에 확인 가능한 것:
- `S0`, `REJ`, 짧은 세션 다발 -> 포트 스캔/정찰
- NXDOMAIN 급증 -> DGA/DNS tunneling 의심
- 비정상 SNI/JA3 -> 악성 툴 fingerprint 단서
- Suricata alert 발생 전후 같은 IP의 세션 흐름 역추적

### 3.2 Suricata와의 역할 보완

| 도구 | 질문 | 강점 |
|---|---|---|
| Suricata | "이 패턴이 악성인가?" | 룰 기반 탐지/차단 |
| Zeek | "이 IP가 그 전에 뭘 했는가?" | 세션/프로토콜 메타데이터 축적 |

실전에서는 둘을 함께 써야 의미가 커진다.

- Suricata alert 발생
- 같은 `src_ip`를 기준으로 Zeek `conn.log`, `dns.log`, `ssl.log` 역조회
- nginx/Wazuh 로그와 합쳐 공격 타임라인 재구성

### 3.3 Grafana에서 가능해지는 것

Zeek 도입 후 추가 가능한 대표 패널:

| 패널 | 의미 |
|---|---|
| `conn_state` 분포 | 스캔/비정상 연결 상태 가시화 |
| 시간대별 신규 세션 수 | 자동화 공격/급증 탐지 |
| DNS Top 도메인 | 서버의 외부 질의 행위 추적 |
| NXDOMAIN 비율 | 비정상 DNS 패턴 감지 |
| TLS SNI Top N | 어떤 도메인으로 TLS 연결되는지 확인 |
| JA3 목록 | 악성 툴 fingerprint 추적 |
| Zeek notice/weird | 포트 스캔, 프로토콜 이상 증적 |

## 4. Zeek 도입 시 손해와 비용

Zeek는 유용하지만 공짜는 아니다.

| 항목 | 비용/리스크 |
|---|---|
| CPU/RAM 사용량 증가 | 세션/프로토콜 분석 비용 발생 |
| 로그량 증가 | `conn.log`와 `dns.log`가 지속적으로 쌓임 |
| Loki 저장량 증가 | 보존 기간이 길수록 디스크 부담 커짐 |
| 쿼리 복잡도 증가 | 대시보드와 상관분석 설계 필요 |
| 운영 난이도 증가 | Zeek/Suricata/Wazuh 간 역할 구분 필요 |

핵심 판단:
- `Suricata`만 쓰면 "탐지"는 되지만 "행위 재구성"이 약하다.
- `Zeek`까지 쓰면 "가시성"은 크게 늘지만 저장/튜닝 부담이 생긴다.

---

## 5. 로그량은 얼마나 증가하는가

정확한 수치는 실제 트래픽에 따라 달라진다. 다만 홈서버 기준으로는 아래 범위를 현실적인 추정치로 볼 수 있다.

| 단계 | 추가 로그 유입량(원본 기준) | 설명 |
|---|---:|---|
| Zeek만 추가 | `+0.2 ~ 1.0 GB/day` | `conn.log`, `dns.log`, `ssl.log` 중심 |
| Suricata만 추가 | `+0.1 ~ 1.0 GB/day` | `eve.json`에서 `alert/flow/http/dns/tls` 증가 |
| Suricata + Zeek + Wazuh 안정화 | `+0.3 ~ 1.5 GB/day` | 저트래픽 홈서버 기준 |
| 중간 트래픽 환경 | `+1.5 ~ 5 GB/day` | 봇 스캔/세션 수 증가 시 |
| 스캔 다발/공격 집중일 | `+5 ~ 15 GB/day` 가능 | flow/conn 이벤트 폭증 시 |

현재 대비 증가 비율로 보면:
- 저트래픽 기준 `2 ~ 4배`
- 스캔이 자주 들어오면 `4 ~ 8배`

증가 원인:
- Zeek는 "경고"가 아니라 "연결"을 남긴다.
- Suricata는 `alert` 외에도 `flow`, `dns`, `tls`, `http` 이벤트를 남긴다.
- Wazuh가 안정화되면 호스트 이벤트도 함께 늘어난다.

## 6. 왜 100% 전부 볼 수 없는가

핵심은 "도구가 부족해서"가 아니라 "관측 자체의 물리적 한계" 때문이다.

### 6.1 네트워크 레이어

| 한계 | 설명 |
|---|---|
| TLS/E2EE 암호화 | 패킷은 보여도 본문(payload)은 기본적으로 못 봄 |
| 미수집 인터페이스 | 모든 NIC/가상 인터페이스를 다 물지 않으면 누락 가능 |
| 패킷 드롭 | 고부하 시 커널/캡처 버퍼에서 드롭 가능 |
| 로컬 loopback/컨테이너 내부 통신 | 캡처 위치에 따라 일부가 안 잡힐 수 있음 |

즉, Zeek/Suricata를 붙여도 `메타데이터 전수`에는 가까워질 수 있어도 `본문 전수`는 불가능하다.

### 6.2 시스템 레이어

| 한계 | 설명 |
|---|---|
| 기본 syslog/Wazuh만으로는 syscall 전수 불가 | 정책 기반 이벤트만 수집 |
| 커널 레벨 이벤트 폭주 | auditd/eBPF를 전면 적용하면 성능 비용 급증 |
| 수집기 장애 가능성 | agent/promtail 죽으면 공백 발생 |

즉, 호스트에서 "모든 시스템 행위"를 전부 보려면 `auditd`나 `eBPF`가 필요하지만, 그 순간 성능/안정성 비용이 커진다.

### 6.3 애플리케이션 레이어

| 한계 | 설명 |
|---|---|
| 앱이 로그를 안 남기면 안 보임 | 미들웨어 밖에서 일어난 내부 행위는 누락 가능 |
| 우회 경로 존재 | nginx 로그만 믿으면 우회 연결은 놓칠 수 있음 |
| 암호화된 요청 본문 | HTTPS 뒤의 앱 페이로드 전수 확보는 별도 계층 필요 |

즉, Grafana에 보이는 것은 "수집된 것의 시각화"이지, "세상 모든 행위의 전수 재현"이 아니다.

## 7. 단계별 가시성 수준

| 단계 | 조건 | 예상 가시성 |
|---|---|---:|
| 현재 | 로그 기반 스택만 운영 | `30 ~ 45%` |
| B 단계 | `Wazuh + Suricata + Zeek` | `60 ~ 75%` |
| C 단계 | `B + auditd/eBPF + rolling PCAP + Arkime` | `80 ~ 90%+` |

해석:
- `B` 단계는 실용적인 균형점이다.
- `C` 단계는 전수에 더 가까워지지만, 저장량/성능/운영 난도가 급격히 상승한다.

---

## 8. 왜 C 단계가 특히 무거운가

### 8.1 rolling PCAP

패킷 원본을 통째로 디스크에 쓰기 때문에 트래픽에 정비례해서 용량이 증가한다.

예시:
- 평균 `20 Mbps` 지속 -> 약 `216 GB/day`
- 평균 `100 Mbps` 지속 -> 약 `1.08 TB/day`

### 8.2 Arkime

Arkime는 단순 저장이 아니라 세션을 파싱하고 인덱싱해서 검색 가능하게 만든다.

부하 원인:
- 패킷 파싱 CPU
- 메타데이터 인덱싱 RAM/CPU
- 검색 저장소 디스크 I/O

### 8.3 auditd / eBPF

이들은 syscall, 프로세스, 네트워크 이벤트를 매우 세밀하게 수집한다.

부하 원인:
- 이벤트 발생 빈도 자체가 매우 높음
- 필터링이 약하면 로그 폭주
- 잘못 설정하면 애플리케이션 성능에 직접 영향

그래서:
- `B`는 운영 가능한 수준으로 튜닝 가능
- `C`는 설계 미스 시 서버를 실제로 느리게 만들거나 저장소를 터뜨릴 수 있다

---

## 9. 최종 판단

현재 프로젝트에서 Zeek는 "당장 필수"는 아니지만, 목표가 아래처럼 바뀌는 순간 가치가 커진다.

- 누가, 언제, 어떻게 접근했는지 장기적으로 추적하고 싶다
- Suricata alert 이전 정찰 행위까지 보고 싶다
- DNS/TLS 메타데이터로 C2/우회 흔적을 보고 싶다

따라서 현재 기준 최적 순서는 다음과 같다.

1. `Wazuh` 안정화
2. `Suricata` 도입 및 alert-only 운영
3. `Zeek` 추가로 세션/프로토콜 가시성 확보
4. 필요할 때만 `auditd/eBPF`, `rolling PCAP`, `Arkime`로 확장

이 프로젝트에서 Zeek의 가치는 "탐지 도구 하나 추가"가 아니라,  
"네트워크 행위 재구성이 가능해지는 관측 계층 추가"에 있다.
