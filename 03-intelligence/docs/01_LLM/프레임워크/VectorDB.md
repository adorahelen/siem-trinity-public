# Vector DB vs 일반 DB

> 작성일: 2026-03-19
> 관련 파일: `embedder.py` — ChromaDB 사용 이유

---

## 핵심 차이

| | 일반 DB (PostgreSQL 등) | 벡터 DB (ChromaDB 등) |
|--|----------------------|---------------------|
| **저장 단위** | 행(row), 컬럼(column) | 벡터(숫자 배열) + 원본 텍스트 |
| **검색 방식** | 정확한 값 일치 (`WHERE ip = '...'`) | 의미 유사도 (`유사한 벡터 찾기`) |
| **질문 유형** | "218.92.0.23 이 포함된 로그 찾아" | "SSH 공격과 관련된 로그 찾아" |
| **인덱스** | B-Tree, Hash | HNSW (벡터 근접 탐색) |

---

## 직관적 비교

```
일반 DB 검색:
  "SSH" 라는 단어가 있는 로그 → 키워드 완전 일치만 찾음
  "Secure Shell" → 못 찾음 (같은 의미지만 단어 다름)

벡터 DB 검색:
  "SSH 공격 알려줘" → 의미적으로 유사한 로그 찾음
  "Secure Shell brute force", "port 22 attack" 등도 찾아냄
  단어가 달라도 의미가 비슷하면 검색됨
```

---

## 이 프로젝트에서 ChromaDB를 쓰는 이유

```
사용자 질문: "어젯밤 공격 패턴이 이상한 게 있어?"

일반 DB로는:
  어떤 키워드로 WHERE 절을 써야 할지 모름
  "이상한", "패턴" → 검색 불가

ChromaDB로:
  질문을 벡터로 변환 → 의미적으로 유사한 로그 검색
  → "weird", "notice", "alert", "anomaly" 관련 로그 자동으로 찾음
```

## 둘을 같이 쓰는 경우 (하이브리드)

벡터 DB와 일반 DB를 함께 쓰면 더 강력합니다.

```
하이브리드 검색 (2024 트렌드):
  BM25 (키워드 검색)   → "218.92.0.23" 정확한 IP 검색 강점
  +
  벡터 검색            → "SSH 공격" 의미 유사도 검색 강점
  =
  두 결과를 통합 (RRF) → 정확도 + 의미 이해 모두 확보
```

이 프로젝트 향후 개선 방향 ([프로젝트_진화_로드맵.md](./프로젝트_진화_로드맵.md) 참고).

## 대표 벡터 DB 비교

| DB | 특징 | 비고 |
|----|------|------|
| **ChromaDB** | 경량, 로컬 파일 기반, 오픈소스 | 현재 사용 |
| **Pinecone** | 클라우드, 관리형, 대용량 | 유료 |
| **Weaviate** | 오픈소스, 하이브리드 검색 기본 제공 | 자체 서버 필요 |
| **Qdrant** | 고성능, Rust 기반, 오픈소스 | 자체 서버 필요 |
| **pgvector** | PostgreSQL 확장, 기존 DB에 벡터 추가 | SQL과 통합 가능 |
