# AI 학습과 추론 방법론

> 작성일: 2026-03-19
> 이 프로젝트(XDR RAG)의 접근법: **RAG + 프롬프트 엔지니어링**

---

## 두 가지 분류 관점

### 관점 A — 학술/기술적 분류 (이 문서의 원래 접근)

```
LLM 활용 방법
├── 모델 자체를 바꾼다 (학습)
│   ├── Pre-training
│   └── Fine-tuning
└── 모델은 그대로, 입력을 바꾼다 (추론)
    ├── RAG
    ├── Prompt Engineering
    └── Few-shot
```

"어떻게 만들었는가"에 집중. Pre-training 포함. Agent/Rule 누락.

### 관점 B — 실무/운영적 분류 (더 완전한 프레임워크)

```
[Model] 을 제어하는 5가지 방법
├── 학습 (Fine-tuning)   — 모델 가중치를 바꾼다
├── 참고 (RAG)           — 외부 데이터를 실시간 주입한다
├── 지시 (Prompt)        — 질문/역할/형식으로 행동을 유도한다
├── 행동 (Agent / Tool)  — 모델이 직접 도구를 호출하고 행동한다
└── 제어 (Rule / Filter) — 출력을 검증하고 안전하게 제한한다
```

"실제 서비스에서 어떻게 제어하는가"에 집중. Pre-training 제외(빅테크 영역). **Agent와 Rule이 추가됨.**

### 왜 매칭이 안 되는가

| 항목 | 관점 A | 관점 B |
|------|--------|--------|
| Pre-training | ✅ 포함 | ❌ 제외 (실무자 영역 아님) |
| Fine-tuning | ✅ | ✅ |
| RAG | ✅ | ✅ |
| Prompt Engineering | ✅ | ✅ (지시) |
| Few-shot | 별도 항목 | Prompt의 하위 기법으로 흡수 |
| **Agent / Tool** | ❌ 누락 | ✅ 포함 |
| **Rule / Filter** | ❌ 누락 | ✅ 포함 |

관점 B가 실무에서 더 완전한 프레임워크입니다.

## 전체 구조 (관점 B 기준으로 재정리)

---

## 1. Pre-training (사전 학습)

LLM을 **처음부터** 만드는 과정입니다.

```
인터넷 전체 텍스트 (수조 토큰)
    │
    ▼
Transformer 구조로 "다음 단어 예측" 반복 학습
    │  수개월, GPU 수천 장, 수백억 원
    ▼
Base Model (llama3.1, qwen2.5 등)
```

**누가 하는가:** Meta, Google, Alibaba, Anthropic 등 빅테크
**개인/스타트업이 하는가:** 사실상 불가능 (비용, 인프라)

---

## 2. Fine-tuning (파인튜닝)

Pre-training된 베이스 모델을 **특정 도메인/작업에 맞게 추가 학습**시키는 것.

```
Base Model (llama3.1:8b)
    │
    ▼ 도메인 데이터로 추가 학습
    │  (의료 논문, 법률 문서, 보안 로그 등)
    ▼
Fine-tuned Model (의료 특화 LLM, 법률 LLM 등)
```

### 파인튜닝 종류

| 방식 | 설명 | 비용 |
|------|------|------|
| **Full Fine-tuning** | 모델 전체 가중치 재학습 | GPU 수십 장, 수일 |
| **LoRA** | 일부 레이어만 학습 (경량화) | GPU 1~2장, 수시간 |
| **QLoRA** | LoRA + 양자화, 메모리 절약 | MacBook Pro급도 가능 |
| **RLHF** | 사람 피드백으로 정렬 학습 | ChatGPT가 쓴 방식 |

### 파인튜닝의 장단점

```
장점: 모델이 도메인을 "체화" → 프롬프트 없이도 전문 답변
단점: - 학습 비용 (시간, GPU)
      - 데이터 준비 (라벨링 등)
      - 최신 데이터 반영 불가 (재학습 필요)
      - 과적합(catastrophic forgetting) 위험
```

---

## 3. RAG (Retrieval-Augmented Generation)

모델은 **건드리지 않고**, 추론 시점에 외부 데이터를 검색해서 컨텍스트로 주입.

```
질문
 │
 ▼
외부 데이터 검색 (벡터 DB, 검색엔진 등)
 │  → 관련 문서/로그 추출
 ▼
[검색 결과 + 질문] → LLM
 │
 ▼
답변
```

### ⭐ 이 프로젝트의 방식

```
사용자 질문
    │
    ▼ nomic-embed-text로 벡터 변환
ChromaDB에서 유사 보안 로그 검색
    │
    ▼
[로그 컨텍스트 + 실시간 현황 + 질문] → llama3.1:8b
    │
    ▼
한국어 보안 분석 답변
```

### RAG의 장단점

```
장점: - 모델 학습 불필요 → 비용 거의 없음
      - 실시간 데이터 반영 가능 (로그 동기화만 하면 됨)
      - 환각(hallucination) 감소 (근거 문서 기반 답변)
단점: - 검색 품질에 의존 (나쁜 검색 → 나쁜 답변)
      - 컨텍스트 길이 제한 (너무 많은 문서는 주입 불가)
      - 추론 시간 증가 (검색 → LLM 2단계)
```

---

## 4. Prompt Engineering (프롬프트 엔지니어링)

모델도, 데이터도 그대로 — **질문/지시 방식만 최적화**.

### 주요 기법

**① Zero-shot**
```
"다음 로그에서 공격 IP를 추출하시오: ..."
→ 예시 없이 바로 질문
```

**② Few-shot**
```
"다음 예시처럼 분석하시오:
 예시1: [로그] → [분석 결과]
 예시2: [로그] → [분석 결과]
 실제: [로그] → ?"
→ 예시를 프롬프트에 포함시켜 패턴 유도
```

**③ Chain-of-Thought (CoT)**
```
"단계별로 생각하시오:
 1. 먼저 공격 유형을 파악하고
 2. 영향 범위를 분석하고
 3. 위험도를 판단하시오"
→ 추론 과정을 명시적으로 유도 → 복잡한 분석에 효과적
```

**④ System Prompt (역할 부여)**
```
"당신은 리눅스 서버 보안 분석 전문가입니다.
 한국어로 답변하고, 위험도를 명시하십시오."
→ LLM의 페르소나와 출력 형식을 고정
```

### ⭐ 이 프로젝트에서 사용 중인 기법

```python
# rag_chain.py → get_system_prompt()

System Prompt  : 역할 부여 (보안 전문가), 응답 방식 구분
Few-shot 없음  : RAG가 실제 로그를 컨텍스트로 제공하므로 불필요
CoT 부분 적용  : "위험도 명시 → 권고 조치 포함" 순서 강제
```

## 5. 방법론 비교 및 선택 기준

| | Pre-training | Fine-tuning | RAG | Prompt Engineering |
|--|------------|------------|-----|--------------------|
| **비용** | 수백억 원 | 수십만 원~ | 거의 없음 | 없음 |
| **최신 데이터** | 불가 | 불가 (재학습 필요) | ✅ 실시간 | ✅ 실시간 |
| **도메인 특화** | ✅ 강함 | ✅ 강함 | 중간 | 약함 |
| **구현 난이도** | 최상 | 높음 | 중간 | 낮음 |
| **환각 감소** | 보통 | 보통 | ✅ 강함 | 보통 |

### 실전 선택 기준

```
데이터가 자주 바뀐다          → RAG
특정 말투/형식이 필요하다      → Fine-tuning 또는 Prompt Engineering
비용이 없다                  → RAG + Prompt Engineering  ← 이 프로젝트
최고 품질이 필요하다           → Fine-tuning + RAG 병행
```

## 6. 조합 사용 (현실에서의 접근)

실제 상용 서비스는 하나만 쓰지 않고 조합합니다.

```
ChatGPT / Claude:
  Pre-training → RLHF Fine-tuning → System Prompt → (RAG 일부)

GitHub Copilot:
  Fine-tuning (코드 특화) → RAG (현재 파일 컨텍스트)

이 프로젝트 (XDR RAG):
  Base Model (Meta Pre-training) → RAG (Loki 로그) → Prompt Engineering
```

## 5-1. Agent / Tool (행동) — 관점 A에서 누락된 항목

모델이 답변만 하는 게 아니라 **직접 도구를 선택하고 실행**하는 방식.

```
사용자: "현재 공격 IP를 조회하고 차단 명령까지 실행해줘"
    │
    ▼
LLM이 판단:
  1. loki_query("SSH 공격 IP") 호출 → 결과 확인
  2. firewall_block("218.92.0.23") 호출 → 차단 실행
  3. 결과 요약 → 사용자에게 보고
```

**대표 패턴:** ReAct (Reason + Act), Function Calling, Tool Use
**대표 제품:** LangChain Agent, AutoGPT, Devin(AI 개발자), Claude Tool Use

**이 프로젝트:** Agent 미사용. 읽기 전용(Loki API GET만) 설계이므로 의도적으로 제외.

---

## 5-2. Rule / Filter (제어) — 관점 A에서 누락된 항목

모델 출력을 **외부에서 검증하고 제한**하는 안전장치.

```
LLM 출력
    │
    ▼
[Rule / Filter 레이어]
    ├── 욕설/유해 콘텐츠 필터
    ├── 출력 형식 검증 (JSON 파싱 실패 → 재시도)
    ├── 길이 제한
    └── 허용된 명령어만 실행 (Agent 안전장치)
    │
    ▼
최종 사용자에게 전달
```

**대표 도구:** Guardrails AI, LlamaGuard, NeMo Guardrails, Constitutional AI(Anthropic)
**이 프로젝트:** 시스템 프롬프트 내 규칙으로 부분 적용 (위험도 형식 강제, 데이터 없으면 "확인되지 않습니다" 명시).

## 7. 이 프로젝트에서 각 방법론의 역할 (관점 B 기준)

| 방법 | 이 프로젝트 적용 여부 | 내용 |
|------|---------------------|------|
| 학습 (Fine-tuning) | ❌ 미사용 | 비용/복잡도 절감, Meta Pre-training 모델 그대로 사용 |
| 참고 (RAG) | ✅ 핵심 | Loki 로그 → ChromaDB → 실시간 컨텍스트 주입 |
| 지시 (Prompt) | ✅ 적용 | 한국어 강제, 위험도 형식, 대화/분석 모드 구분 |
| 행동 (Agent) | ❌ 미사용 | 읽기 전용 설계 (서버 조작 금지 원칙) |
| 제어 (Rule) | ⚠️ 부분 적용 | 시스템 프롬프트 내 형식 규칙 (별도 필터 레이어 없음) |

```
[Meta Pre-training] llama3.1:8b 베이스 모델
         │
         ▼
[RAG]    Loki 로그 동기화 → ChromaDB 검색 → 컨텍스트 주입
         │
         ▼
[Prompt] 보안 전문가 역할, 한국어, 위험도/권고 형식 강제
         │
         ▼
         답변 출력
```
