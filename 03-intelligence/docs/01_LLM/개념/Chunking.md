# Chunking 전략

> 작성일: 2026-03-19
> 관련 파일: `embedder.py` — `chunk_size=20`

---

## Chunking이란?

긴 로그 텍스트를 LLM과 벡터DB에 넣기 위해 **일정 크기로 잘라내는 것**.

```
[전체 로그 10,000줄]
    │
    ▼ chunk_size=20
[청크1: 1~20줄]
[청크2: 21~40줄]
[청크3: 41~60줄]
...
→ ChromaDB에 각각 저장
```

---

## 왜 잘라야 하는가?

LLM은 한번에 처리할 수 있는 텍스트 길이에 한계가 있습니다 (Context Window).
10,000줄 로그를 통째로 넣으면 → 한계 초과 → 에러 또는 앞부분 잘림.

또한 벡터 검색의 정확도는 청크가 **하나의 의미 단위**일 때 높아집니다.
너무 크면 여러 주제가 섞여 검색 정확도 하락.

---

## chunk_size=20 의 의미

이 프로젝트에서 청크 하나 = **로그 20줄**.

```python
# embedder.py
def chunk_logs(logs, chunk_size=20):
    # 시간순으로 정렬된 로그를 20줄씩 묶음
```

보안 로그 20줄은 대략 **수 분~수십 분 분량의 이벤트**로,
하나의 공격 흐름이나 이상 징후를 담기에 적절한 크기.

---

## chunk_size 크기별 트레이드오프

| chunk_size | 장점 | 단점 |
|-----------|------|------|
| **작음 (5~10)** | 검색 정밀도 높음 | 문맥 부족, 청크 수 과다 |
| **적정 (20~50)** | 문맥 + 정밀도 균형 | — |
| **큼 (100+)** | 문맥 풍부 | 검색 정확도 하락, 토큰 초과 위험 |

---

## 청킹 전략 종류

| 전략 | 방식 | 이 프로젝트 |
|------|------|-----------|
| **Fixed-size** | 줄 수/글자 수로 고정 분할 | ✅ 현재 사용 |
| **Semantic** | 의미 단위로 분할 (문단, 섹션) | 문서에 적합 |
| **Sliding Window** | 청크 간 겹침(overlap) 허용 | 문맥 연속성 필요 시 |
| **Recursive** | 구분자(\n\n → \n → 문장) 단계적 분할 | LangChain 기본 |

---

## 이 프로젝트에서 튜닝 포인트

```python
# 더 정밀한 검색이 필요하면
chunk_size=10   # 청크 작게

# 공격 흐름 전체를 문맥으로 담으려면
chunk_size=50   # 청크 크게

# Sliding Window 적용 시 (청크 간 5줄 겹침)
chunks = []
for i in range(0, len(logs), chunk_size - 5):
    chunks.append(logs[i:i+chunk_size])
```
