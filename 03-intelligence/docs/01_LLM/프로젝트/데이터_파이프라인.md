# 데이터 파이프라인 — 로그 수집에서 LLM까지

> 작성일: 2026-03-20
> 이 프로젝트 전체 스택 — 문서화된 LLM 레이어 앞단의 인프라 레이어

---

## 전체 파이프라인

```
[서버 로그 생성]
  Suricata, Zeek, Wazuh, Nginx, fail2ban, syslog 등
      │
      ▼
[수집] Promtail
  로그 파일 tail → Loki로 전송
      │
      ▼
[저장] Loki
  로그 저장소 (타임스탬프 + 레이블 + 원문)
  포트 3100, Tailscale 100.x.x.x
      │
      ▼ HTTP GET (Tailscale VPN)
[쿼리] loki_client.py
  LogQL 쿼리 → JSON 응답 파싱
      │
      ▼
[벡터화] embedder.py
  청크(20줄) → nomic-embed-text → 벡터
      │
      ▼
[저장] ChromaDB
  ~/.xdr/chroma_db/ (로컬 맥북)
      │
      ▼
[검색 + 생성] rag_chain.py
  질문 벡터 검색 → LLM 컨텍스트 주입 → 답변
```

---

## 1단계 — 로그 생성 (서버)

```
SIEM 스택이 생성하는 로그 유형:

Suricata:  네트워크 이벤트 (flow, dns, tls, alert)
           형식: JSON (eve.json)

Zeek:      네트워크 분석 (conn, dns, http, ssl, notice, weird)
           형식: TSV → logfmt

Wazuh:     보안 알림 (level 7~15 = High)
           형식: JSON

fail2ban:  SSH 자동 차단 (Ban/Unban)
           형식: 텍스트

Nginx:     HTTP 접근 로그 (GeoIP 포함)
           형식: logfmt

syslog:    시스템 전체 로그 (ERROR/WARNING/CRON)
```

---

## 2단계 — 수집 (Promtail)

```
역할: 로그 파일을 읽어 Loki로 전송하는 에이전트

핵심 기능:
  tail -f 방식으로 로그 파일 실시간 감시
  레이블(label) 부착: job="suricata", level="8" 등
  Loki HTTP API로 전송 (POST /loki/api/v1/push)

레이블의 중요성:
  Loki 쿼리 시 {job="auth"} 처럼 필터링 기준
  이 프로젝트의 19개 job 레이블이 모두 Promtail이 붙인 것
```

---

## 3단계 — 저장 (Loki)

```
역할: 로그 저장소 (Prometheus의 로그 버전)

일반 DB와 다른 점:
  인덱스: 레이블만 인덱싱 (내용 전체 인덱싱 X)
  저장: 원문 로그를 타임스탬프 + 레이블과 함께 압축 저장
  장점: 메모리/디스크 사용량 매우 적음
  단점: 내용 기반 전문 검색 느림 (그래서 RAG가 필요)

접근:
  서버 내부: 127.0.0.1:3100
  맥북에서: 100.x.x.x:3100 (Tailscale VPN 통해)
```

---

## 4단계 — 쿼리 (loki_client.py)

```
역할: Loki HTTP API를 Python으로 호출

사용 API:
  GET /loki/api/v1/query_range   시간 범위 쿼리
  GET /loki/api/v1/query         인스턴트 쿼리 (집계)

LogQL 예시:
  {job="auth"} |= "Invalid user"          SSH 공격
  {job="suricata"} | json | alert_severity="1"   Critical alert
  {job="wazuh", level=~"([7-9]|1[0-5])"}  고위험 알림

반환 형식: [{"timestamp": "...", "labels": {...}, "line": "..."}]
```

---

## 5단계 — 벡터화 (embedder.py)

```
역할: 로그 텍스트 → ChromaDB 벡터 저장

청킹:
  로그 20줄씩 묶어 하나의 청크
  시간순 정렬 유지
  형식: "timestamp | job | log_line"

임베딩:
  nomic-embed-text (Ollama) → 768차원 벡터
  중복 방지: 청크 내용의 SHA256 해시를 ID로 사용

현재 상태:
  1,963 청크 저장 (2026-03-19 초기 동기화)
  소스: auth, fail2ban, suricata, wazuh, zeek_conn,
        zeek_dns, zeek_notice, kern, nginx_access_enriched
```

---

## 6단계 — RAG (rag_chain.py)

```
역할: 검색 + LLM 답변 생성

흐름:
  질문 → nomic-embed-text → 질문 벡터
      │
      ▼ ChromaDB MMR 검색 (fetch_k=20 → k=5)
  관련 로그 청크 5개 추출
      │
      ▼ 실시간 보완 (선택적)
  Loki에서 최신 24시간 현황 직접 조회
      │
      ▼ LLM
  [시스템 프롬프트 + 검색된 로그 + 실시간 현황 + 질문]
  → llama3.1:8b → 한국어 보안 분석 답변
```

## 왜 Loki만 쓰고 로그 파일을 직접 안 가져오나

```
제약 원칙: 서버 파일 직접 접근 금지 (scp/rsync 금지)

이유:
  1. 서버 부하 최소화
  2. 보안 (SSH 키 관리 복잡도 감소)
  3. Loki API가 이미 인증/필터링 제공
  4. 실시간 쿼리 가능 (파일 복사 불필요)

결과:
  맥북 ↔ 서버 통신: HTTP GET만 사용
  서버 측 변경: 전혀 없음
```
