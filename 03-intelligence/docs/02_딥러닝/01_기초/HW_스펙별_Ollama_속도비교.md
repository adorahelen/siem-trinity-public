## 핵심 인사이트

### Decode 속도 — 맥북 M3 ≥ DGX Spark (8B 모델)

```
DGX Spark는 70B+ 대형 모델에 최적화된 장비
8B 소형 모델은 M3 통합 메모리의 높은 대역폭이 유리하게 작용

DGX Spark Decode: 38 tok/s
맥북 M3 Decode:   50~70 tok/s  ← 오히려 빠름

→ 현재 프로젝트(llama3.1:8b) 기준
  맥북 M3가 DGX Spark보다 체감 응답속도 비슷하거나 빠를 수 있음
```

### Prefill 속도 — DGX Spark 압도적 우위

```
긴 컨텍스트(로그 수천 줄)를 한번에 처리할 때:
  DGX Spark: 7,614 tok/s
  맥북 M3:   ~300~500 tok/s  (약 15~25배 차이)

→ RAG에서 긴 청크 주입 시 DGX가 유리
→ 현재 프로젝트 규모(청크 수십~수백 tok)에서는 체감 차이 크지 않음
```

### 서버(CPU 전용)에서 Ollama 실행하면 안 되는 이유

```
Ryzen 5500GT CPU 전용 Decode: 3~6 tok/s
→ 100 토큰 응답에 약 17~33초
→ 실사용 불가 수준

맥북에서 실행하는 현재 구조가 맞음
```

### 모델 크기별 M3 가능 여부

```
llama3.1:8b   (~5GB)   → ✅ M3 16GB 충분, 50~70 tok/s
qwen2.5:14b   (~9GB)   → ✅ M3 16GB 가능, 30~50 tok/s (추정)
deepseek-r1:14b (~9GB) → ✅ M3 16GB 가능
gemma3:27b    (~17GB)  → ❌ M3 16GB 불가 (메모리 초과)
llama3.1:70B  (~40GB)  → ❌ M3 16GB 불가
qwen3:32B     (~20GB)  → ❌ M3 16GB 불가

한계선: 약 12~14B 모델이 M3 16GB의 실용적 최대
```

## 이 프로젝트 관점 정리

```
현재 구조 (맥북 M3 + llama3.1:8b):
  Decode 50~70 tok/s → 실사용에 충분
  DGX Spark 대비 Decode 동급 또는 우위
  비용: 0원 (이미 보유한 맥북)

단기 업그레이드 여지:
  모델: llama3.1:8b → qwen2.5:14b (.env 한 줄 변경)
  → M3 한계 내 최대 성능

장기 업그레이드 시나리오:
  HW: M3 → M4 Pro (36GB) → 32B 모델 가능
  HW: M3 → M4 Max (128GB) → 70B+ 모델 가능
  서버에 GPU 추가 → 별도 Ollama 서버 구성 가능
```

## 실제 질문별 소요 시간 예시

### 예시 1 — "안녕 네 이름이 뭐야?" (단순 질문)

```
입력 토큰:  약 10개
출력 토큰:  약 30개 ("안녕하세요! 저는 llama입니다. 무엇을 도와드릴까요?")
```

| HW | 입력 처리 | 답변 생성 | 총 소요 시간 |
|----|----------|----------|------------|
| DGX Spark | 10 ÷ 7,614 = 0.001초 | 30 ÷ 38 = 0.8초 | **~0.8초** |
| 맥북 M3 | 10 ÷ 350 = 0.03초 | 30 ÷ 60 = 0.5초 | **~0.5초** |
| 서버 CPU | 10 ÷ 50 = 0.2초 | 30 ÷ 4.5 = 6.7초 | **~7초** |

→ 짧은 질문에서는 맥북 M3가 DGX Spark보다 빠름 (Decode 속도가 병목)

---

### 예시 2 — "현재 내 서버에서 보안상 이상 없어?" (RAG 질문)

```
입력 토큰:  질문 20개 + RAG 로그 컨텍스트 2,000개 = 약 2,020개
출력 토큰:  약 300개 (보안 분석 답변)
```

| HW | 입력 처리 (2,020 tok) | 답변 생성 (300 tok) | 총 소요 시간 |
|----|---------------------|-------------------|------------|
| DGX Spark | 2020 ÷ 7,614 = 0.3초 | 300 ÷ 38 = 7.9초 | **~8초** |
| 맥북 M3 | 2020 ÷ 350 = 5.8초 | 300 ÷ 60 = 5초 | **~11초** |
| 서버 CPU | 2020 ÷ 50 = 40초 | 300 ÷ 4.5 = 67초 | **~107초** |

→ RAG 질문에서는 DGX Spark가 유리 (Prefill 속도가 병목)

---

### 결론 — 질문 유형별 병목 정리

```
짧은 질문 (토큰 적음):
  답변 생성(Decode)이 병목
  → 맥북 M3 ≥ DGX Spark

RAG 질문 (컨텍스트 길음):
  입력 처리(Prefill)가 병목
  → DGX Spark 유리 (~8초 vs ~11초)

서버 CPU:
  어느 경우든 실사용 불가 (단순 질문도 7초, RAG 질문 107초)

이 프로젝트 현실:
  RAG 질문 기준 맥북 M3에서 약 10~15초 소요
  실사용에 충분한 수준
```

## 용어 정리

```
Prefill (tok/s):
  입력 프롬프트 전체를 처리하는 속도
  RAG에서 컨텍스트를 LLM에 주입하는 단계
  → 높을수록 첫 토큰 출력이 빠름 (TTFT: Time To First Token)

Decode (tok/s):
  답변 토큰을 하나씩 생성하는 속도
  사용자가 체감하는 "타이핑 속도"
  → 높을수록 답변이 빠르게 출력됨

q4_K_M:
  4비트 양자화 (K-means, Medium)
  모델 크기 ~50% 축소, 품질 손실 최소
  실사용 표준 양자화

q8_0:
  8비트 양자화
  모델 크기 ~75% 축소, 품질 거의 동일
  메모리 여유 있을 때 사용
```
