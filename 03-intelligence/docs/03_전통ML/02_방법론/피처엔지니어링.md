# 피처 엔지니어링 (Feature Engineering)

> 작성일: 2026-03-20
> 전통 ML의 핵심 단계 — LLM에서는 불필요한 이유 포함

---

## 피처(Feature)란?

ML 모델이 학습하는 **입력 변수**.
사람이 원시 데이터에서 의미 있는 숫자를 직접 뽑아내야 합니다.

```
원시 데이터 (서버 로그):
  "2026-03-19 02:13:45 auth Invalid user admin from 218.92.0.23 port 41234"

피처로 변환 (사람이 설계):
  hour          = 2          (새벽 시간대)
  is_invalid    = 1          (Invalid user 여부)
  src_ip_prefix = 218        (IP 앞자리)
  src_port      = 41234
  username      = "admin"    → 인코딩 필요
```

---

## 피처 엔지니어링이란?

원시 데이터를 모델이 학습할 수 있는 **숫자 형태의 피처로 변환**하는 과정.
전통 ML에서 모델 성능의 80%는 피처 품질에 달려있다고 할 정도로 중요합니다.

---

## 주요 작업 종류

### 1. 피처 선택 (Feature Selection)

```
원시 데이터에 100개의 컬럼이 있어도, 실제 예측에 도움이 되는 건 10개뿐일 수 있음.
불필요한 피처 → 노이즈, 과적합, 속도 저하

방법:
  - 상관관계 분석 → 결과와 연관 없는 피처 제거
  - 중요도 분석 (랜덤 포레스트 feature importance)
  - 도메인 지식 기반 선택 (보안 전문가가 "포트 번호가 중요하다" 판단)
```

### 2. 피처 변환 (Feature Transformation)

```
문제: 모델은 숫자만 이해, 텍스트/날짜/카테고리는 변환 필요

텍스트 → 숫자:
  "admin", "root", "ubuntu" → 0, 1, 2 (레이블 인코딩)
  또는 원핫 인코딩: "admin" → [1,0,0], "root" → [0,1,0]

날짜/시간 → 숫자:
  "2026-03-19 02:13" → hour=2, is_weekend=0, is_night=1

IP 주소 → 숫자:
  "218.92.0.23" → 국가코드(KR=0, CN=1), IP 앞자리(218)
```

### 3. 피처 스케일링 (Feature Scaling)

```
문제: 피처마다 단위가 다름
  포트 번호: 0~65535
  패킷 크기: 0~1500
  접속 횟수: 0~1000

모델은 숫자 크기에 민감 → 포트 번호가 무조건 더 중요하게 취급될 수 있음

해결:
  정규화 (Min-Max): 모든 값을 0~1 사이로
  표준화 (Z-score): 평균 0, 분산 1로
```

### 4. 피처 생성 (Feature Creation)

```
기존 피처를 조합해 새 피처 만들기:

  시간당 접속 횟수 = 총 접속 / 관찰 시간
  동일 IP 고유 포트 수 = 포트 중복 제거 count
  공격 비율 = Invalid 횟수 / 전체 접속 횟수

→ 도메인 지식이 있어야 좋은 피처를 만들 수 있음
```

## 피처 엔지니어링의 어려움

```
1. 도메인 지식 필수
   → 보안 로그에서 어떤 피처가 중요한지 알려면 보안 전문가 필요

2. 반복 실험
   → 어떤 피처가 효과적인지 실험 → 평가 → 수정 반복

3. 데이터 변화에 취약
   → 공격 패턴이 바뀌면 피처 재설계 필요

4. 시간 비용
   → 실제 ML 프로젝트에서 전체 시간의 70~80%를 차지
```

---

## LLM에서는 왜 불필요한가

```
전통 ML:
  사람 → 피처 직접 설계 → 모델 학습

LLM (Transformer):
  원문 텍스트 → 토크나이저가 자동으로 숫자로 변환
  모델이 어텐션 메커니즘으로 스스로 중요한 패턴 학습
  → 피처 엔지니어링 단계 자체가 없음
```

이것이 LLM의 혁신 중 하나입니다.
"사람이 피처를 설계하는 병목"을 제거하고, 원시 텍스트를 바로 입력으로 받습니다.

---

## 이 프로젝트와 비교

```
이 프로젝트 (LLM + RAG):
  Loki 로그 원문 → 그대로 ChromaDB에 저장 → LLM에 텍스트로 전달
  피처 엔지니어링: 없음

만약 전통 ML로 구현했다면:
  Loki 로그 → 시간, IP, 포트, 이벤트 유형 등 수동 파싱
  → 숫자 피처 테이블 생성 → 모델 학습
  → 새 공격 패턴마다 피처 재설계 필요
```
